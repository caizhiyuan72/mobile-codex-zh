# Codex CN：旧版签名丢失后的安全升级方案

> 状态：迁移设计；尚未实现或通过真机验收。**不要卸载或清除目前已安装的 V5。**

## 已核实的情况

- 已发布 V5: `v0.3.9-cn.5`，包名 `dev.mobilecodex.app.zhcnv3`，versionCode 76。
- V4/V5 旧构建脚本引用同一私钥文件 `codex-cn-signing-key-private.pem`；当前工作目录和保存的源码交付包中没有找到该文件。
- V5 APK 的签名证书不能反推出签名私钥。
- V5 包内存在 **项目导出**（`projects.export` / `ui.projects.exportFile`），但没有完整的 API 服务商、密钥和全局设置导出入口。V5 API 密钥使用 Android Keystore 加密，无法保证卸载后恢复。
- 完整原版源码已恢复到 `upstream-source/`；**Codex CN V5 修改版的全部 Android 原生变更仍需补全**。
- Android 原生更新通常需要同 applicationId、同签名（或合法密钥轮换证明）及递增 versionCode；签名丢失时不能把新签名 APK 当作原版的无损更新。

## 方案 A（优先）：寻找原签名密钥

仅在用户本人的合法备份、以前的编译设备或隔离的私有存储中搜索 `.pem` / `.jks` / `.keystore`。验证候选私钥对应的证书公钥与 V5 APK 签名证书一致后，才用于下一次构建。**不要将私钥提交到公开仓库、Issue、日志或 Release**。

成功后：保留包名 `dev.mobilecodex.app.zhcnv3`，递增版本号，通过覆盖安装在真机验证设置与项目数据完整。

## 方案 B（原密钥确实不可用）：并行安装、逐项迁移

1. 保持 V5 **已安装、可登录、可访问数据**。
2. 基于已恢复的上游源码重建 Codex CN 功能，完成第三方 API、中文、思考强度、子智能体等 Android 原生改动的源码恢复。
3. 为新应用分配不同的 applicationId，例如 `dev.mobilecodex.app.cn.next`。生成独立、长期使用的新签名私钥，安全离线备份；构建服务仅通过私有 Secrets 访问密钥。
4. 给新应用实现 **配置导入、项目导入、迁移验收**。旧应用里能导出的项目逐个导出；对服务商名称、URL、模型列表和用户选择进行可核对的迁移。**不要把 API Key、会话令牌打进不加密的日志或公开文件**。
5. API 密钥在新应用由用户从服务商后台重新取得并录入。旧密钥曾出现在聊天记录中，应考虑轮换；Keystore 加密密钥不假设可以跨包名恢复。
6. 先并排运行 V5 和新应用，逐项验收 API 连接、项目、聊天与设置。没验收成功前不卸载 V5；**绝不以 root 绕过 Android 签名验证来冒充正规覆盖升级**。
7. 新应用后续所有版本保持新包名和新签名证书，以正常 APK 更新方式维护。

## 验收门槛

- [ ] V5 依然可以打开；没有被卸载、降级或清除数据
- [ ] 旧签名私钥恢复并与 V5 证书匹配，或者选择并行迁移方案
- [ ] 新 APK 来自完整对应源码，Android 编译与测试通过
- [ ] 新 APK 能在用户设备安装、启动，并完成试运行
- [ ] 旧版项目和非机密设置迁移记录逐项验证
- [ ] 新 API Key 能正常调用 API，旧 API Key 没有意外暴露
- [ ] 新版的下一次升级使用同包名同签名，覆盖安装后数据完整
- [ ] GPL-3.0 相应源码、许可声明及构建说明齐备

当前结论：**没有找到 V5 原签名密钥，无法保证原包名直接更新；迁移还未完成。**
